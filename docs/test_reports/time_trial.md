# Time Trial（系统侧计时 + 「30min → auto」诚实化）

- 报告日期：2026-09-07
- 数据：`docs/test_reports/time_trial_data.json`（本报告内嵌的确定性链数字来自它）
- LLM 解析延迟数据：`logs/llm_calls.jsonl`（256 条累计，2026-09-08T04:46Z 截止）

## 0. 一句话口径（先给结论，避免被误读）

**这套系统不声称"5 分钟拿单"。** 它声称的是三件可复现的事：

1. **确定性交付链（LeadJSON → 候选产品 → 报价 → 行程 Markdown → 风险检查 → 销售草稿）**：
   进程内实测 **mean 1.5ms / range [1.4, 1.6]ms**（3 样本 × 5 次，warm cache，非 LLM 环节）。也就是原来靠人手工做的"排单 + 算价 + 起草稿"这一大段，自动化后在**亚毫秒到毫秒级**跑完。
2. **唯一 LLM 环节（原始客户文本 → LeadJSON）**：真实调用日志显示单次 median ≈ 25s、mean ≈ 30s、长尾至 ~138s。这是每个 lead 端到端耗时里**真实存在的主项**，不是广告数字。
3. **旧人工基线"约 30 分钟/单"是自估、非实测**（见 §2）；曾被口头使用的"5 分钟"口径**没有测量依据，本报告撤销它**。

## 1. 口径与方法

| 数字 | 含义 | 测量方式 | 状态 |
|---|---|---|---|
| ~30 min/单 | 旧人工 Excel 流程（估） | 无秒表 | **自估、非实测** |
| 1.5ms | 确定性交付链 | 本报告实测 | 实测（3 样本 × 5 次） |
| ~25–30s | LLM 文本→LeadJSON 单次 | `llm_calls.jsonl` 实测 | 实测（256 条累计日志） |
| 5 分钟 | 曾被使用的自动化耗时 | 无 | **撤销**（无测量依据） |

确定性链计时脚本：`scripts/time_full_chain.py`。它**只测进程内确定性链**（生产路径 `run_full_chain_for_lead`，
即 `POST /api/v2/lead-full-chain` 的同一函数），先 warmup 一次以加载数据文件/缓存再计时；**不重复调用 LLM**
（LLM 延迟单列，绝不与"自动链"混淆）。

## 2. 旧基线（自估，非实测）

我无法替你回测"旧流程人工 Excel 排单"的真实耗时——那时没有留秒表记录。因此：

- 「约 30 分钟/单」保留为**自估区间**：拆法大约是 客户需求整理 ~10min + 产品匹配 ~8min + 算价核对 ~6min
  + 行程/邮件起草 ~6min。**这是估计，不是本次实测**，任何人问起都应如此表述。
- 一切**未测量的"5 分钟"口径全部撤下**。唯一有依据的自动化口径见 §4。

## 3. 系统侧实测（确定性交付链）

方法：3 条代表性合成样本（干净上海夫妻 / 北京带导游+私家车可选 / 西安 70 岁老人+兵马俑必去），各 warmup 1 次后计时 5 次。

| 样本 | mean | range | 推荐产品 | 总价(USD) | 需人工复核 |
|---|---|---|---|---|---|
| shanghai_couple_2d_clean | 1.5ms | [1.4, 1.6] | SH-P-01 | 180.0 | 否（干净单） |
| beijing_3d_guide_car_optional | 1.5ms | [1.4, 1.6] | BJ-P-02 | 5500.0 | **是** |
| xian_2d_senior_pace | 1.4ms | [1.4, 1.5] | XA-P-01 | 2745.0 | **是** |
| **整体** | **1.5ms** | **[1.4, 1.6]** | — | — | — |

复现：`python3 scripts/time_full_chain.py --runs 5 --out docs/test_reports/time_trial_data.json`

## 4. LLM 解析延迟（真实日志实测）

`logs/llm_calls.jsonl` 256 条累计（冒烟 + 开发期 + v1/v2 两轮全量 eval），模型 `qwen3.8-27b`：

| 指标 | 值 |
|---|---|
| 成功 / 总 | 243 / 256 |
| latency median / mean | 24.6s / 30.3s |
| latency min / max | 11.9s / 138.0s |
| ReadTimeout（基础设施偶发慢响应） | 13（harness 单次重试兜住） |

证据与字段说明见 `docs/AI_EVIDENCE_llm_log_excerpt.md`。

## 5. 端到端口径合成（诚实版）

每个 lead（从原始客户文本）的实际耗时可**分两段**如实陈述：

```
客户文本 → LeadJSON       LLM 单次解析（真实网络调用）   ~25–30s median（日志实测；偶发 >100s，已重试）
LeadJSON → 交付草稿        确定性引擎链（纯进程内计算）   ~1.5ms（实测）
剩余人工                   风险检查标记的人工复核清单     数条 flag（见 §6），秒级阅读
```

- **能说**："从结构化 Lead 到候选产品+报价+行程+风险检查+销售草稿，系统自动生成在毫秒级；唯一网络 LLM
  环节 ~30s/单；每单剩少量需销售确认的复核项。"
- **不能说**："5 分钟一键出单"——LLM 单次就 ~30s，加上人的复核，5 分钟口径没有测量，也不是这套自动链要背的承诺。

## 6. 还剩什么人工（风险检查 flag 逐条）

确定性链不会替人做所有决定；`RiskCheckResultJSON.human_review_required` 会把**需要销售/计调确认**的项挑出来单列，
人只需读清单而非重做整单。本次 3 样本中 2 条触发了 flag：

| 样本 | 触发 | 内容 |
|---|---|---|
| beijing_3d_guide_car_optional | `[PRIVATE_CAR_NEEDS_CONFIRMATION]` | 私家车偏好未确认；报价前需销售与客户确认 |
| xian_2d_senior_pace | `[PRIVATE_CAR_NEEDS_CONFIRMATION]` | 同上 |
| xian_2d_senior_pace | `[SENIOR_TRAVEL_PACE_RISK]` | 检出 70 岁老人同行；复核节奏与拥挤等行动风险 |
| shanghai_couple_2d_clean | — | 干净单，无人工 flag |

## 7. 局限（不回避）

- 确定性链 1.5ms 是**单租户、进程内、warm cache、纯 Python 规则**的稳态耗时；不含真实多用户下的 DB/
  网络/IO 排队，也不能代表 API 层到客户端的全链路时延。
- 3 条样本为**合成文本**（由 lead-parse 评测集派生、映射到真实产品），非真实历史询单。后续拿到真实询单
  文本可替换 `SAMPLE_LEADS` 复测（口径不变）。
- LLM 延迟是**累计日志**统计（含开发期），非单独一次干净 run；但 v1/v2 两轮全量 run 的窗口均值与全量一致
  （median 24.8s / 26.6s），结论稳健。
- 旧人工 30min 基线是自估，无法实测——这是本报告的边界，已在 §2 明示。
