> 这是目录整理前的分析快照；实际新位置与已完成项见 [目录说明](project-structure.md) 和 [路线图](roadmap.md)。

分析日期：2026-10-07。本文记录本次代码、目录、数据、文档与本地验证结果，作为整理和迁移的依据；现行功能说明仍以 `architecture.md` 和实际代码为准。

## 1. 结论

这个项目已经具备前后端分离的原型：Streamlit 界面通过 HTTP 调用 FastAPI，后端完成询单解析、产品匹配、成本计算、行程生成、风险检查、邮件草稿和付款管理。全栈改造的主要工作是规范工程边界、建立可靠存储与用户权限，再建设新的网站界面。

值得保留的资产是业务规则、产品与成本数据、结构化输入输出，以及已有评测。当前目录则混合了运行代码、历史实验、产品材料、个人作品集和求职资料，不能直接作为新网站的发布目录。

建议顺序：**建立可复现基线 → 整理目录和文档 → 拆分后端与统一路径 → 数据库和身份权限 → 一个完整的新网页流程 → 上线验证**。网站最终定位可以在过程中逐步确定，不必现在决定全部页面。

本次只新增这份分析报告，没有移动或删除已有文件，没有修改业务代码，也没有部署。

## 6. 上线前明确需要补齐的工程能力

### P0：先解决复现与打包

1. **Docker 打包不完整。** `Dockerfile` 复制了 `api_main.py`，但遗漏其直接导入的 `llm_client.py`、`workflow_logger.py`；还没复制运行时使用的 `docs/prompts`。按当前配置构建出的应用缺必要文件，不能据此认定后端能正常启动。本次未实际构建镜像。
2. **半定制数据缺少版本管理。** `.gitignore` 忽略整个 `data/`。已经跟踪的标准产品与成本文件仍在 Git 中，但 `data/custom/` 四份运行数据未被跟踪。干净 checkout 缺少这项功能的必要输入。
3. **忽略规则缺口。** 没有统一忽略 `.venv/`、`node_modules/`、`.next/`、`dist/`、`.env.*` 等未来开发产物；现有子项目部分自带规则，但根目录仍需规范。应明确放行可发布演示数据与 `.env.example`。
4. **配置与路径散落。** API、引擎、提示词、日志和脚本按各自 `__file__` 推断根目录，迁入 `backend/` 后会改变路径含义。应集中配置代码资源、演示数据与可写存储的位置。
5. **复现环境不充分。** 后端依赖只有最低版本限制；辅助脚本中的 `pandas`、`httpx` 等也没有完整归类。应区分后端运行依赖、旧界面依赖、实验依赖和开发工具，固定已验证版本。

### P1：从单人原型变成网站

1. **用户与权限。** 当前只校验一个共享 API Key，没有账号、组织或记录归属。Streamlit 请求从服务器发出，密钥保存在服务端；改成浏览器请求后，不能直接把这个共享密钥放到公开前端配置。需按运营端或游客端定位设计身份和权限。
2. **可靠存储。** 付款使用整份 JSON 读取后覆盖写入，没有事务与并发保护；询单、报价、行程没有完整业务数据库记录。需数据库、变更迁移、持久化目录与备份机制。
3. **可追踪的工作流。** 人工确认接口是追加日志，`reviewer` 为调用方填写；完整链路的 `workflow_id` 在函数内产生，却不在 `FullChainResponse` 返回。现状尚不是基于用户身份、记录版本和审核状态的完整业务流程。
4. **调用与等待。** AI 路由是 `async def`，内部却调用同步 `requests.post`；慢调用会占用事件循环。Streamlit AI 请求超时为 45 秒，后端超时可配置且还可能修复重试，存在界面先超时的问题。需统一等待策略和并发处理，再按实际需求决定是否引入任务队列。
5. **接口边界。** CORS 当前为通配来源且允许 credentials；异常响应直接返回异常文字；客户原文仅设最小长度、未设最大长度。需在新网站实际访问方式下收紧来源、统一错误返回与输入限制。
6. **发布检查。** 根目录暂无主业务 CI；只有个人站点的发布工作流。部分评测脚本打印分数并写报告，但未在失败时显式返回非零退出码，不宜直接当作发布门禁。

这些是已从当前实现确认的缺口，不代表需要马上引入微服务、Redis、复杂容器编排或大量新工具。先做一个可维护的模块化后端即可。

真实客户、供应商与付款数据应位于独立的可写存储位置，不与上述 `data/demo/` 混用。个人作品集和求职材料可保留在单独资料位置；不要求在第一步永久删除。

为了减少同时变动，后端先只提取配置、HTTP 路由和业务服务；数据库层在真正加入持久化时再建设。不要一次创建大量空目录。

## 9. 分阶段执行与验收

| 阶段 | 具体工作 | 完成检查 |
|---|---|---|
| 0. 基线 | 保存现有变动、明确可发布数据、记录测试与接口 | 不丢本地文件；能够区分当前功能与实验 |
| 1. 整理 | 更新忽略规则；处理两组精确重复；归档个人材料与实验；精简文档入口 | 运行代码依赖可解析；数据重建输入仍可定位；不改变计算结果 |
| 2. 后端规范化 | 迁入 `backend/`；抽出产品匹配、渲染、完整工作流；统一配置与资源路径；修打包配置 | 旧 Streamlit 可调用；现有 API 契约保持；规则基线通过；干净 checkout 可复现 |
| 3. 最小业务存储 | 根据首批用户定义记录归属；保存询单、报价快照、行程和审核状态；付款按需求迁移 | 重启不丢数据；不同用户访问边界明确；数据库可以迁移和备份 |
| 4. 新网页完整流程 | 先做“输入询单 → 确认需求 → 匹配与报价 → 复核 → 保存”的一个流程 | 页面、接口、数据库字段一致；成功、失败、等待均可操作；构建通过 |
| 5. 上线 | 前后端运行、同源转发或明确跨域配置、持久化、进程托管与部署检查 | 服务器重启仍工作；关键业务结果可保存与恢复；有更新与回退方法 |

目录整理是下一阶段的直接工作。产品定位暂不确定，不阻碍前两阶段；但数据库权限和新页面设计前，需要确定首批用户是谁。

## 10. 定位尚未确定时的选择空间

| 方向 | 当前资产匹配程度 | 后续主要新增工作 |
|---|---|---|
| 内部销售/计调工作台 | 最直接，当前界面和规则基本服务这个用户 | 账号权限、客户/询单管理、报价版本、审核、供应商记录 |
| 面向游客的需求收集与方案网站 | 可复用询单和方案引擎，但现有流程偏运营 | 游客体验、解释与确认、隐藏内部成本、分享方案、运营后台 |
| 展示 AI 工作流的公开 Demo | 最容易做一个可演示的版本 | 脱敏种子数据、示例询单、明确结果边界、限制模型调用消耗 |

当前证据更支持从运营工作台的完整流程开始，因为业务规则和复核环节已存在；这是便于复用的起点，不是最终产品定位决定。公开 Demo 也可以作为这一流程的受限演示入口。
